# v0.4.4 — Syncthing upload status that reflects reality

After a game exits, the plugin backs up your save and then tells you whether Syncthing has moved it to your other devices. Until this release that report was largely fiction: the status strip announced **SYNCTHING COMPLETE** on a timer, without having observed a single thing any peer did. This release makes the post-game status describe what actually happened.

## Upload status

- **COMPLETE now means a device actually received the backup.** Previously the plugin watched for `RemoteDownloadProgress` events as evidence of outbound transfer, saw none, and fell through to a detection grace period — publishing COMPLETE roughly 22 seconds after the backup regardless of whether any peer had the data. Device logs showed the pattern on every post-game run: `SYNCTHING PREPARING` and then COMPLETE, with no upload ever observed. The plugin now tracks per-peer `FolderCompletion` reports for the watched folder and holds **SYNCTHING UPLOADING** until a connected device confirms it has the save. (#5bc0c6f, #fbd4caa, #a3e717f)

- **COMPLETE requires one connected device to confirm, not all of them.** Waiting for every connected peer meant the slowest device set how long you waited, and the status strip stays on screen for that whole time. A captured run had two peers finish within four seconds of each other and a third take seventeen seconds longer. Completion now publishes once a connected device has the content and has held that state across three consecutive checks. Other devices may still be catching up when the status appears — the README says so plainly, because the guarantee genuinely became weaker. (#7a19f6b)

- **Snapshot pruning no longer delays completion.** Syncthing reports three separate quantities per peer: bytes missing, files missing, and files still to delete. Only the first two mean your save has not arrived; the third is housekeeping as old Ludusavi snapshots are removed. A captured run had every peer holding the save 24 seconds after the backup, followed by four and a half minutes of pruning that ended in a false **UPLOAD INCOMPLETE**. Completion is now gated on missing content alone. Pending deletes and the completion percentage remain in the diagnostics — the percentage cannot be used as a gate because Syncthing reduces it for pending deletes too. (#874a62a, #83045bc, #196cc73)

- **Completion no longer waits fifteen seconds for a folder that is already quiet.** Settling required the backup folder to show no local index activity for fifteen seconds. Measured across seven captures, every post-backup burst finished within 0.111 seconds and nothing arrived late. Post-game settling now uses a three-second window of its own; pre-game keeps the original fifteen seconds because that value also holds game launch, where releasing early risks starting a game before a newer incoming save has landed. End-to-end post-game completion dropped from 27.4 to 18.4 seconds on the same game. (#34a8c4b)

- **A slow or stalled upload now reports itself honestly.** If monitoring ends while a connected device is still catching up, the plugin publishes **LOCAL BACKUP SAVED — SYNCTHING UPLOAD INCOMPLETE** rather than presenting an ordinary slow sync as an API failure. The backend also stops a post-game watch when outstanding need stops decreasing, instead of running to a fixed cap. (#3a6e4c8, #4920826)

## Event subscription

- **Fixed the bug that made all of the above invisible.** Syncthing's `/rest/events` scopes each event `id` to the subscription selected by the `events=` filter, while `globalID` is process-wide, and `since` is matched against the scoped id. The cursor was seeded from an unfiltered request and then used against the filtered subscription, so it sat roughly nine hundred events beyond anything that subscription would ever emit. **The plugin had been receiving no Syncthing events at all**; everything it appeared to detect came from polling folder status. Confirmed on hardware against a reproduced control: the old build seeded cursor 1261 and received nothing while the fixed build seeded 324, advanced to 347, and tracked all three peers. (#52eaf87)

- **A recreated subscription no longer silences the stream.** Syncthing discards idle subscriptions, and a new one restarts its id sequence at 1. A cursor held from the previous subscription would sit above every new id and the watch would go quiet for the rest of its life. The watcher now detects the reset and re-seeds. (#86ac8f8)

## Diagnostics

- **Transition-only logging for post-game uploads.** Each change in peer state logs one line with the connected peer count, how many are still missing content, how many have deletes pending, and the aggregate outstanding totals. Device identifiers, folder paths, and raw payloads are never logged. With **Debug Logging** enabled the watcher keeps observing after completion so the remaining propagation appears in the log; the published status is identical either way. (#b0f64b1, #a46c7a9)

## Security

- Cleared **GHSA-fxqj-rqcc-2cmp** (`postcss`) and **GHSA-mwcw-c2x4-8c55** / **GHSA-2v37-7h3g-55p8** (`nanoid`) by upgrading rather than suppressing. `nanoid` 3.3.17 was inside the repository's 14-day dependency quarantine, so it was added to `minimumReleaseAgeExclude` as a pinned single-version entry following the existing `postcss@8.5.18` precedent — every other release of both packages stays quarantined, and no advisory is ignored. `pnpm audit` reports no known vulnerabilities. Build-environment exposure only; never shipped in the plugin ZIP. (#d44c2a1)

## Notes

The post-game upload path was verified on a Steam Deck with three connected peers across several runs. The stall window and the post-game watch ceilings were not reached during that verification and remain unexercised in practice.
